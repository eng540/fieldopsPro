# ADR-003: Monotonic Progress Policy (Financial Safety)

## Status
**Accepted** — Sprint-0 Baseline

## Context
In construction/WASH projects, progress percentages directly translate to financial payments (IPC). Allowing arbitrary decreases in progress creates financial and audit risks.

## Decision
We enforce **Monotonic Progress** for all BoQ completion percentages, with controlled exceptions via the Rework workflow.

## Policy Rules

### Rule 1: Automatic Increase
- Any increase in `completion_pct` is accepted if ≥ current server value
- Server timestamp wins in case of near-simultaneous updates

### Rule 2: Automatic Rejection (Decrease)
- Any decrease in `completion_pct` is rejected with `409 Conflict`
- Error message: "Progress cannot decrease. Use Rework Flag with justification."

### Rule 3: Controlled Decrease (Rework)
- Decrease is permitted ONLY if:
  1. `rework_flag = true`
  2. `rework_reason` is provided (min 20 characters)
  3. `rework_authorized_by` is a valid Project Manager or Org Admin
  4. Audit entry is created automatically

### Rule 4: Timestamp Usage
- `device_timestamp` is used for display and logging only
- `server_timestamp` is used for conflict resolution
- `Vector Clock` detects true concurrency (same server timestamp window)

## Governance Integration
- Monotonic Progress is a **pre-condition** for Governance Engine evaluation
- If progress is invalid, Governance Engine receives `HOLD` as pre-state
- Rework decisions trigger re-evaluation of Governance rules

## Consequences

### Positive:
- Prevents accidental or malicious financial manipulation
- Creates clear audit trail for any "backward" movement
- Aligns with construction industry standards (WASH, IPC practices)

### Negative:
- Engineers may find workflow restrictive if legitimate remeasurement is needed
- Requires PM availability for rework authorization
- Edge case: What if PM is offline and engineer discovers critical error?
  - **Mitigation:** Emergency Rework Flag with auto-escalation to Org Admin
