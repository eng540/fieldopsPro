# ADR-001: Modular Monolith over Microservices

## Status
**Accepted** — Sprint-0 Baseline

## Context
FieldOps V4.0 is transitioning from a single-project application to a multi-tenant SaaS platform. We needed to decide on the overall backend architecture pattern.

## Decision
We will adopt a **Modular Monolith** architecture using FastAPI with strict internal module boundaries.

## Rationale

### Why NOT Microservices (for V4.0):
1. **Offline-First Sync Complexity:** Microservices would make the sync protocol a distributed systems nightmare (eventual consistency across services in offline contexts).
2. **Team Size:** Current team size (< 10 developers) does not justify the operational overhead of microservices (service mesh, distributed tracing, circuit breakers).
3. **Database Transactions:** Financial governance (IPC calculations, payment holds) requires ACID transactions across multiple domains. Distributed transactions (Saga pattern) add unnecessary complexity at this stage.
4. **Deployment Simplicity:** A single deployable unit reduces DevOps complexity for humanitarian contexts where technical staff may be limited.

### Why Modular Monolith:
1. **Clear Boundaries:** Each module (iam, projects, execution, quality, governance, reporting) has its own models, schemas, routers, and service layer.
2. **Future Extraction:** If a module needs to become a standalone service later (e.g., Governance Engine as a shared service across products), the extraction path is clear because boundaries are already enforced.
3. **Single Database:** Multi-tenant row-level security is simpler to enforce in a single PostgreSQL instance than across distributed databases.
4. **Performance:** No network hops between modules. In-process function calls are orders of magnitude faster than gRPC/HTTP between services.

## Consequences

### Positive:
- Faster development cycles
- Simpler testing (single test database)
- Easier debugging and stack traces
- Lower infrastructure costs

### Negative:
- Risk of tight coupling if module boundaries are not enforced
- All modules must scale together (vertical scaling only)
- Technology stack is uniform (cannot use Go for sync engine, Python for ML independently)

## Mitigations
- **A-01 No Cross-Module DB Access:** Modules communicate only via public service functions
- **A-03 Internal Event Bus:** Decoupled communication via domain events
- **A-02 Shared Kernel Discipline:** `core/` package contains only infrastructure, never business logic
