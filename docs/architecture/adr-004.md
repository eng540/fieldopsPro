# ADR-004: JWT Minimalism + Server-Side Authorization

## Status
**Accepted** — Sprint-0 Baseline

## Context
Traditional JWT implementations embed full user roles and permissions in the token. This creates problems when permissions change (stale tokens) or when fine-grained project scoping is needed.

## Decision
We adopt **JWT Minimalism**: tokens carry identity and references only; all authorization decisions are made server-side.

## JWT Payload Structure
```json
{
  "sub": "15",
  "org_id": 7,
  "session_id": "uuid",
  "token_version": 3,
  "iat": 1717072800,
  "exp": 1717073700,
  "type": "access"
}
```

**Explicitly NOT in JWT:**
- `role` (may change; server reads from DB)
- `projects` (assignment may change; server reads from `ProjectUser` table)
- `permissions` (RBAC matrix is server-side)

## Server-Side Authorization Flow
1. Decode JWT → extract `sub`, `org_id`, `session_id`
2. Check `session_registry` → is session revoked?
3. Query `User` + `ProjectUser` tables → determine effective role and project scope
4. Apply request-level authorization based on endpoint + resource + action
5. Log authorization decision in audit trail

## Token Lifecycle
- **Access Token:** 15 minutes, stored in RAM only (never localStorage)
- **Refresh Token:** 7 days, HttpOnly Secure Cookie, rotated on every use
- **Session Registry:** Redis-backed, supports instant revocation

## Consequences

### Positive:
- Instant permission revocation (no waiting for token expiry)
- Dynamic project assignments (engineer reassigned to new project = immediate effect)
- Smaller JWT payload
- Reduced token tampering surface

### Negative:
- Database query required for every authorized request (caching mitigates)
- Slightly higher latency (~5-10ms for Redis cache hit)

## Mitigations
- Redis cache for user permissions (TTL: 5 minutes)
- Connection pooling for PostgreSQL
- Async permission loading during request lifecycle
